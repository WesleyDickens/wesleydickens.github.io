When an AI assistant cites the wrong policy

The answer cited a real document. It was the retired policy, saved beside its replacement.

A partner told me her firm’s assistant had hallucinated. She had asked about an internal policy, the answer came back wrong, and she knew it was wrong because she had written the current policy herself the previous spring.

We opened the cited file. The assistant had quoted it word for word, but it was the 2019 version, sitting in the same folder as the current one.

The pilot had failed to answer her question correctly. Finding the retired document explained one reason why. A citation showed where the answer came from; it did not establish that the policy still applied.

Replacing the model would not, by itself, resolve which policy the firm considered current. That decision needed to be represented in the material the assistant searched.

What does “client” mean here?

Consider a firm where finance counts a client as a billing entity, the partners count a family or group of related LLCs, and marketing counts a closed-won deal in the CRM. Those definitions can each serve a purpose. Trouble starts when someone asks for “the client count” without specifying which one they need.

A report can document the definition it uses, though reports can disagree too. An assistant with access to all three systems needs a way to choose the relevant definition or ask for clarification. Otherwise, two partners can ask similar questions and receive different counts without seeing why.

A fluent explanation can make that disagreement harder to spot. A wrong answer may cite real records and contain no obvious calculation error. The person reading it needs to know what was counted, not just where the records came from.

What reaches the search index

Many document assistants split files into passages and use numerical representations of the text to find passages related to a question. A close match in wording or meaning does not necessarily identify the current, complete, or applicable document.

A superseded policy may resemble the question more closely than its replacement. Modified dates can also mislead: resaving an old file can make it appear newer than the policy in force. The system needs to use reliable version or status information, or search a collection that excludes retired policies.

Scanned documents introduce a different problem. A scan without a text layer can be missed by an ingestion process that only extracts existing text. OCR can read text from the image, but it must be included in the process and its output checked.2 Executed agreements and signed letters deserve attention because the copy that matters may be a scan. A document created digitally can also parse badly; neither format guarantees usable extraction.

Folder context matters too. /Clients/Former/ and /Clients/Active/ tell a reader something that the text inside a file may not. If an ingestion process drops that context, passages from an archive can look as relevant as passages from the current folder.

Chunking does not have to discard metadata. Systems can carry document information onto each chunk.3 Check whether yours preserves the context you need and whether retrieval actually uses it. Keeping a path as a citation is not the same as using it to exclude a retired document.

Access deserves a separate check. A file that was rarely discovered may become easy to surface through an assistant. Microsoft introduced Restricted SharePoint Search as a temporary measure while administrators review permissions.1 I discuss the scoping decisions in Decide what the assistant can read before you buy it.

There is useful information to recover as well. A note such as spoke with Jim, board meets in May, revisit after can help explain a relationship that structured fields miss. But terse notes leave room for interpretation. Keep the source text beside any extracted field and check a sample by hand.

Questions to ask before you buy anything

Start with people who know the records. Bring in whoever manages the systems for questions about extraction and history.

  1. Write down three real questions. Use sentences someone would type, such as Which clients haven’t we billed this quarter? The wording will expose definitions and sources that a broad use-case label leaves out.
  2. Ask three people to define the central noun. Client, matter, engagement, household. Ask separately, in writing. If the definitions differ, decide which belongs to each question and how the answer should identify it.
  3. Follow one client through the systems. Look in billing, the CRM, the document store, email, and any working spreadsheet. Note different spellings and decide which system is authoritative for each field when records disagree.
  4. Try to recover an important field’s value from a year ago. A status, fee arrangement, or rate will do. Check what history exists before promising trend analysis. If it is missing, discuss snapshots with the system owner, including what to retain and who maintains them.
  5. Open the folder where an answer should live. Look through the last twenty files for near-duplicates and version numbers. Try selecting text in a scan. If you cannot, check whether the ingestion process performs OCR and inspect what it extracts.
  6. Decide how to detect a wrong answer. Specify the check, who runs it, and what happens when it fails. Do not rely only on users volunteering that something went wrong.

Separate file cleanup from decisions about the records

Deduplicating files, running OCR, and excluding an archive from an index can be scoped as implementation work. Deciding what counts as a client, which system is authoritative, or whether an old fee arrangement still applies requires someone with authority over those records.

A warehouse does not remove that distinction. I have built them; the definition still has to be agreed before the schema can represent it. Assign those decisions to named owners and settle the ones the pilot depends on before testing its answers.

If a practice group already maintains a suitable collection, start there. A narrower set of questions may be answerable without cleaning the entire drive. Ask a prospective vendor which sources and questions it would leave out, and what that would prevent users from doing.

For the policy question, the test is concrete: can the assistant return the current clause and identify the version it used? Repeat the check after the next policy update. That is the behavior the partner needed from the pilot.
